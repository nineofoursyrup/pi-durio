## 沿用的首版与授权边界

首版保持 macOS arm64 本机 Node CLI、DeepSeek `deepseek-flash`、coding/TUI/headless/eval 共用 runtime；普通 coding 可信本机执行，正式 eval 使用经验证的受限环境。继续复用 durable 的 loop、存储、恢复与用量，不新增并行 agent 平台、常驻 optimizer、日常 critic 或自动更新器。

首版完整路径是 coding 与检查、退出/恢复、用量/trace 查询、长期原文及上下文压缩、手动 eval、显式 improve 的建议→选择→执行验证→结果留存。阶段性交付不表示这条路径已经完整。

设计可交接、产品实现验证、真实 provider 验证和发布分别记录。缺少真实凭据或付费授权时，可继续独立的本地实现和确定性检查，但相关真实验收保持未运行；设计确认不授权模型调用、候选执行或发布。

### Q1：首版真实端到端验收的深度

已确认：首版完成须有真实 DeepSeek coding/工具轮转，以及真实 improve 分析与选中执行闭环。#6 的四类固定任务通过真实模型运行，产生实际产物和检查证据；不应改动的反例以目标状态未被改变等真实证据验收，不强求产生 patch。TUI/headless 接线和 macOS Terminal 交互分别核验，不要求同一任务在每个入口重复支付模型调用。另以可控的小型项目完成 improve 取证→用户选中→必要验证→正式写回或适用的新任务生效→重新打开记录核验。

improve 可以使用已知可改进问题的 fixture，选择确定性修复，不以模型必须发现新优化或测得性能收益作为首版门槛。候选仍须来自实际分析并经选择，不能以预填候选替代真实分析结果。零候选保持合法，只是该次不能证明执行链已经完成；可用受控输入独立验证分支，报告分清真实模型与合成证据。性能候选的改善和启用继续受 #6/#7 的预定规则约束。

真实验收批次在执行前固定案例、要求、版本、次数、预算和可观察结果；保留首次失败及所有计划项。修复后运行新的、关联原失败的验收记录，不挑成功输出改写旧结论。首版任务达标不自动成为行为改善或普遍稳定性证明；重复次数和费用额度由实际批次计划决定，本轮不发明统一测试数量。

### Q2：轻量实测如何进入首版接受判断

已确认：沿用先测基线，不把未知数值拖成实现前置条件。交付可复核的体积/启动/内存/记录增长与开销报告，并在用户本机试用后明确接受或指出需改进项；只有技术验收已完成、尚欠用户试用决定时，才称“技术验收完成，日用接受待确认”。不通过一项未校准的 MB/ms 总分宣布轻量达标，也不建设通用性能门禁平台。

正确性、授权、原文保留、内存/显示有界等既定硬约束仍须通过。正常完整原文引起的磁盘增长单独报告，不被当作必须自动清理的故障。若实测暴露不可接受的资源或体验问题，用具体证据界定下一步优化目标；目标及门槛在相应优化试验前固定，不能事后修改门槛制造改善。

使用同一份验收记录引用现有 run、trace、eval 和 improve 产物，不另建验收平台。每项至少能追查要求/源合同、候选内容与执行条件、检查方式及实际结果、证据位置与缺口；一个证据可支持多项，但不能超出其实际验证范围。

| 日用接受 | 技术验收完成，用户依据测量报告及本机试用明确接受 | 未进行 |

用户提出阻碍日用的问题、要求先修正时，保持待接受；完成修正及必要复测后，再由用户明确接受，不能把反馈或修正计划当作接受结果。

验收项区分通过、失败、未运行、受阻、证据不足；不适用只能用于确实不属于已确认范围的分支，并说明依据。不能因为功能未做、环境不可用或没有预算就把首版必需项写成不适用。检查应验证“预期失败被正确处理”还是“要求任务成功”；故障注入中正确阻断是产品行为通过，被测任务本身仍保留其失败或未知事实。

所有必需项均有支持才能声称技术验收完成。任一已证实的恢复/权限/原文/计量/隔离等硬约束失败都阻止该结论，不能用较小体积或较低费用抵消。缺少真实凭据、授权、Terminal 观察或有效隔离证据时，将相关项明确留为未运行/受阻/证据不足，其余独立检查可继续。未知原因不能被 UI 的完成提示或 agent 自报成功覆盖。

四类代表任务各自必须满足预先固定的要求，所声明验收批次的全部计划项与结果都进入报告；失败、取消或未运行项不能挑出后声称整批通过。允许依据首次失败修复并重新验证受影响范围，产生关联的新记录；其他仍适用的确定性检查直接复用。随机模型结论按预定计划重复，不能凭一次成功宣布稳定或改善，也不为了凑出通过无限重跑。技术验收仅支持已声明案例和环境，不承诺任意语言/项目的总体成功率。

正式 eval 能力验收须证明隔离、可信评分、预算与失败分类实际工作，并以已知结果的对照材料检查改善/退化/无明显差异/证据不足的判定路径。受控的确定性材料可以检验 runner 与判定实现，不能冒充随机模型改善证据；不要求首版必须找到一个性能更好的真实候选。

候选工件须可取得，包括必要源码或分发产物、依赖 lock、有效配置/指令、相关 dirty 输入及 fixture/grader 的实际内容；单独 hash 不够。每份证据记录适用版本和环境，验证后相关内容变化则原结果只支持原内容。证据引用遵循 #5 的完整性/固定保留，不能只留已删除的临时目录。凭据值不进入交接、报告或版本内容。

轻量报告按 #2 统一口径列出自有维护代码、生产安装与分发体积、冷启动、空闲/代表性长会话 RSS、记录增长、写盘/查询、大输出及三类工作用量/费用。记录机器、Node/依赖、终端、输入负载、测量过程及重复数据；区分本地和网络/模型耗时，无法分离时说明限制。费用仍为带时间与来源的估算。必需的本地测量未取得时不声称报告完整，provider 未提供的用量则按合同保留 unknown，并限制相应成本判断。

## 可交接的实现依赖顺序

这是工程起点，不新增产品范围，亦不代表已经授权实现。

1. **验证关键接线可行性**：锁定真实安装工件，验证公开 API、只读历史/恢复前检查与能力边界；尽早探查一个现成 eval 隔离机制及 macOS Terminal 的关键输入能力。若要维护 fork、换核心、放宽隔离/恢复保证才能工作，先带证据重开相应设计，不默默降级。
2. **最小 runtime 与基础记录同步形成**：实现 headless、小型 coding 路径、所有权、退出/中止/恢复；从首次持久运行就保留必要身份、原文和用量，不能到后期才补造历史。
3. **接入 TUI 与可查询记录**：共用 runtime，落实队列、恢复面板、上下文压缩、长历史/大输出有界显示、查询及长期保留。
4. **完成手动 eval**：复用 runtime 和记录，固定四类任务初态，落实一种受限环境、可信评分与预算；明确诊断和正式结果。
5. **完成 improve 选择闭环**：受限分析、候选/决定、临时构造、适用验证、写回/生效、回退和记录重开；依赖的隔离及恢复保证须先具备。
6. **执行整体验收并测量**：按本票合同完成实际工件、真实 provider、Terminal、代表任务与轻量测量，逐项保留状态和缺口，再提交用户本机试用及日用接受。

具体文件拆分、命令名称、报告字段、fixture 数量、页大小和可逆参数由实现 Agent 按既有接口选择，不新增逐项访谈。实际付费批次的预算/次数、测量负载与判定门槛须在对应执行前具体化。
