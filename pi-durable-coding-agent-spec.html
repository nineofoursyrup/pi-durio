CHAPTER 01

阅读契约与结论

本规格汇总本次会话从技术选型、可恢复执行、evals / LLM Ops / tracing，到长期改进与手动 retro 的全部主要结果。目标读者是接手设计或实现的 coding agent；阅读本文不需要访问原会话。

当前推荐主线：使用 pi-durable 构建轻量 coding agent；日常低成本记录运行事实；用户显式调用内置 retro skill 后，获得少量有证据的优化候选；用户选择后，agent 完成所选范围的改动与必要验证，并记录实际结果。

这是一份待实现的设计规格。本次已进行源码与文档研究，未创建或安装目标 agent、retro skill、telemetry adapter 或 eval runner，也未运行目标产品的性能基准。本文里的接口、目录、字段和命令示例，除非明确标注为上游已有 API，均为应用层设计建议。

产品目标、轻量指标与范围

用户要求

ID 要求
U-01 基于 pi-durable 开发 coding agent，尽可能代码精简、体积轻量。
U-02 具备 evals、LLM Ops、Tracing 能力，并长期保留有用记录。
U-03 TUI 体验参考 grok-build；实现参考 pi 官方 durable coding-agent demo。

推荐的首版目标

  • 一个本地运行的进程；无需启动数据库服务器、消息队列或常驻优化服务。
  • 交互式 TUI 与 headless / eval 共用同一 runtime 和工具语义。
  • 保存可恢复会话、已知用量、关键调用轨迹及检查结果。
  • 提供按需查询记录、运行精选 eval、查看结果的最小能力。
  • retro 平时不消耗模型调用；调用后先建议，用户选中后执行。
  • 记录建议、用户决定、改动版本和实际效果，为下一次复盘提供证据。

“轻量”必须分别测量

维度 应记录什么 避免的误解
自有代码 维护的源码规模、模块数、特殊分支和依赖边界 自己写得少，不代表运行依赖少
安装体积 lockfile 下真实安装字节、开发与生产依赖 按需 import 不会自动减少 npm 声明依赖的安装
分发体积 bundle、外置资源、平台原生模块、是否含 runtime 单文件不等于体积小
运行开销 冷启动、空闲 RSS、长会话峰值、TUI 响应 只看初次启动内存不够
观测开销 写盘频率、trace 增量、查询耗时、导出队列大小 记录系统不能无限增长或逐 token 放大
模型成本 coding、retro、eval 各自 tokens、费用与耗时 优化分析本身也有成本
维护成本 新增规则、脚本、平台分支、重复状态 为省少量调用引入复杂平台未必值得

尚未设定任何已批准的 MB、毫秒、tokens 或行数硬阈值。 先测量可运行基线，再据实际瓶颈制定预算；不要把本文的“轻量”宣传成未经测量的数值承诺。

首版不默认引入

常驻 optimizer、每任务 LLM critic、强制第二 reviewer、自动创建并启用 skill、向量数据库、知识图谱、多模型委员会、自动微调或强化学习、完整实验管理平台、自动灰度发布、多进程协作执行框架。完整 Web 运维后台也不是首版必要交付。

CHAPTER 04

推荐系统架构

采用一个薄宿主，把交互入口、运行时、记录和复盘连接起来。不要再包一层与 durable 重叠的 agent loop 或恢复状态机。

层 责任 边界
TUI / CLI 输入、会话选择、流式展示、retro 候选与用户选择 不维护第二份权威任务状态
Controller / host 参数、模型与工具注册、会话所有权、命令路由、执行阶段能力 不重写 durable 内部调度
pi-durable 对话、entries / documents、generation / tool tasks、提交、恢复与 compaction 不自动提供完整应用的登录、skill loader、审计或沙箱
Model adapter 只注册需要的 provider、超时重试配置、真实请求边界观测 同一物理模型 attempt 的用量只记一次；返回 stream 对象不代表请求结束
Tool / env read / write / edit / shell，工作区和执行权限 cwd、worktree 与完整进程隔离是不同概念
本地记录 durable 会话、运行摘要、必要 spans、eval 与 retro 记录 能复用则引用；不要重复存整份 transcript
Eval runner 从固定初态运行任务、收集产物与独立检查 使用产品 runtime；候选不控制自己的评分器
Retro skill 选择证据、诊断、提出候选、解释验证方式 它不是数据库、权限系统或另一个常驻 runtime

技术组合

  • 运行基线：TypeScript / ESM / Node，Node 最低版本以选择的上游版本为准。
  • 核心：@earendil-works/pi-durable。
  • 模型：@earendil-works/pi-ai 的必要 provider 入口。
  • UI：@earendil-works/pi-tui。
  • 记录：durable SQLite；需要查询时增加薄索引或应用记录，而非默认新增 ORM。
  • tracing：可实现 pi-telemetry adapter，也可用薄本地记录接口。运行、模型和工具分别在实际生命周期边界记录；同一个物理 attempt 的用量与终结记录由唯一适配层负责，避免多层包装重复计量。
  • eval：开发工具和数据集，与生产必需依赖分开。

存储的推荐原则是复用，不是强制所有数据塞进上游内部表。 优先使用公开 storage / documents / entries 能力与自有命名空间；如果上游数据库迁移或连接所有权使共库不稳，允许增加一份小型索引库或追加记录。不能为追求“只有一个文件”直接修改上游私有 schema。

CHAPTER 06

Durable、恢复与执行正确性

必须保持的语义

ID 正确性约束 说明
DUR-01 恢复依据 durable 已提交状态 TUI、内存通知和临时事件不是恢复的权威来源。
DUR-02 一个 storage 同时由一个进程拥有 SQLite 文件锁不替代应用会话所有权；durable 本身不提供跨进程 owner lock。
DUR-03 首版避免多个活动写入者共享同一工作区 工具内的文件队列不能覆盖 shell、其他进程或第二个 session。
DUR-04 不把工具副作用描述为 exactly-once 外部修改可能已发生而结果还未持久化。
DUR-05 区分退出与中止 关闭保留待恢复工作；abort 是终止工作，产品文案和快捷键应清楚。
DUR-06 版本与未完成任务兼容 工具语义、prompt 或 runtime 改动不应悄悄影响旧 pending task。
DUR-07 fork 对话不等于复制或回滚工作区 文件、数据库、网络操作需要各自的隔离或回退方案。

工具重放

上游先提交工具执行意图，再运行 execute()。重启时，只有已持久化的 replay 策略和当前工具声明同时为 safe，才走安全重跑路径；未声明时按 unsafe 处理。研究快照中的内置 read / write / edit / bash 都没有显式声明 safe。不要自行把 read 判定为上游已保证安全。S19

中断位置 可能发生的情况 宿主应如何呈现或处理
外部操作前 有执行意图，但实际副作用尚未发生 根据真实 replay 合同恢复，不能盲目推断
外部操作后、结果提交前 文件可能已修改、命令可能已执行 标记结果不确定；优先检查现状或使用幂等键
结果已经提交 已有可用结果 读取已有结果不应再算一次工具调用或模型花费
unsafe 执行中 恢复得到 interrupted 结果 模型可能再次提出操作；宿主仍要处理重复副作用风险

safe 是工具对重复执行的承诺，不是“名字看起来只读”的分类。追加文件、提交、发送网络写请求等操作需要明确的幂等或冲突检查。write 同一路径是否安全也取决于当前内容与外部修改，不能一概设 safe。

beforeTool 不是完整恢复权限门。 当前 safe replay 路径会直接进入执行，不重新调用该 hook。若需要在恢复时检查权限或执行环境，应在 resume 前或 tool / env 边界落实；beforeTool 的 block 产生拒绝结果，也不自动构成可持久化的人类审批工作流。S19

存储保证与局限

  • Node SQLite 适配器使用 node:sqlite，WAL 与 synchronous=NORMAL。已提交事务可承受进程崩溃，但断电或宿主故障可能丢失最新提交。运行时还有 WAL 等辅助文件；备份要保持一致性。S20
  • partial 与 tool output 默认按约 100 ms 间隔合并提交；崩溃可能丢失尚未提交的进度窗口。这个窗口说明的是进度刷新策略，不是所有错误场景下的端到端丢失上界。S01
  • JSONL 是替代选择；研究快照默认不 fsync，可配置更强写入同步。选择前应比较查询、文件增长与崩溃语义。S21
  • demo 由宿主补充 session lock；过期锁处理应沿用成熟机制，不能直接根据 PID 不在就随意夺锁。S22
  • viewState() / watchEvents() 服务 UI。慢消费者落后时会得到 snapshot，不能把 UI 事件流当成无损审计总线或花费账本。S23

工作区、退出与升级

NodeExecutionEnv 的 cwd 不是沙箱；内置路径处理支持绝对路径等形式。对进程、网络、凭证或路径的限制要由具体执行环境落实。worktree 可分离代码版本，却不自动阻止进程读取其他路径。S24 S25

普通单进程宿主退出后，其 durable 调度器不再推进任务；重新打开相同持久化状态后才按恢复语义处理工作。已发出的远端请求或残留子进程是否停止，取决于取消与进程清理机制。若将来需要持续后台调度，再明确 daemon / worker 设计。

推荐为每次任务记录应用、工具、prompt、skill 与设置版本；恢复 pending task 时检查版本兼容。工具或 runtime 候选优先在新任务或兼容的新会话生效。回退 agent 默认版本不等于撤销它已经修改的用户文件。

Tracing 与 LLM Ops

先明确三种数据

数据 回答的问题 不应承担的角色
Durable 会话事实 发生了哪些提交、消息、任务与已知用量 不自动等于 provider 的完整账单
Trace / span 一次执行的耗时、父子关系、错误与重试在哪里 不重新建立一套独立花费来源

建议追踪粒度

层级 建议记录 说明
应用 run 任务类型、会话、目标版本、开始结束与 outcome 区分 coding、retro、eval
LLM attempt provider / model、purpose、真实尝试、耗时、usage、错误 compaction、deferred 请求也有成本
Tool execution task / toolCall ID、工具、起止、退出状态、结果引用 区分逻辑调用、实际执行、恢复和重试
Eval trial case、baseline / candidate、grader、检查与产物 不与真实用户任务混在一个成功率分母
Retro / optimization 输入范围、候选、选择、实验与变更版本 分析本身单独计量

默认不为每个 token 建 span，不把完整 prompts、工具大输出、diff 复制到每个 span。只存摘要和持久化记录引用，必要时按范围读取原文。

埋点的具体坑

  1. pi-telemetry 提供契约，宿主仍需接线。其内存参考实现适合测试，不是有界的长期存储，也没有替代生产耗时记录的完整时钟信息。S13 S26
  2. 在真正的模型调用边界埋点一次。当前 Models.completeSimple() 内部调用 this.streamSimple(...).result()，同时包装这两个入口会双计。S27
  3. 流式调用的 span 必须持续到真实结束、出错或取消；不要在返回 stream 对象时结束，也不要为了记录而额外消费一遍流。
  4. 正常生成、compaction 和 deferred response 取回都应覆盖。provider SDK retry 与 durable retry 是不同层次，记录可观测的真实尝试；无法观察的内部重试标明局限，不能臆造次数。S14 S28
  5. 崩溃后尚未结束的 span 可标记 interrupted / incomplete；恢复的新物理执行用新 span 或 link 表达，不伪装成同一进程持续运行。
  6. durable 内只持久化可序列化 ID 与元数据，不存 span / context 对象。
  7. telemetry 写入或导出失败不能改变业务回调结果、取消原请求或导致工具被重跑；队列必须有界，并能反映遗漏记录。可用上游 conformance 核对适配器。S29

用量账本

pi.usage 是 durable 已提交、已知用量的主要来源，包含记录到的模型响应、工具报告与 compaction。原始 provider 未返回 usage 或进程在提交前崩溃时，外部可能已收费但本地无法完整得知；此时记录完整性与未知项，不能记作零。S30

  • 仅重建已提交状态、重读历史、TUI 重绘和重复导出，不应新增本地费用记账。
  • 恢复过程中真正重新执行的模型请求或收费工具调用，应记录新的物理 attempt 及其已知用量；恢复前已经提交的结果不重复计费。
  • reasoning 是 output 的子集，cacheWrite1h 是 cacheWrite 的子集；不能再次相加。S31
  • 保留 token 分类及费用估算口径、币种、价格版本；provider API 返回的 usage 与基于价格表的本地估算应可区分。模型在自然语言中自报的成本不作为账本事实。
  • 全会话、会话分支、单次用户 run 的汇总范围需要明确；不能把累计会话用量重复归到每个 run。若只有不可靠的前后差值，要标记 attribution 的局限。
  • 如果以后启用子 agent，child 自身账本中的模型费用不能再作为父 subagent tool 的同一笔费用重复上报；工具确实产生的额外费用可另记。S30

可选远程后端

以后可通过 adapter 接 OpenTelemetry / Langfuse 等服务。导出携带稳定身份，以便关联和检测重复；只有后端明确提供并验证了去重语义时才依赖它。OTLP 可能因重发产生重复数据，远程 span 数不能直接充当精确用量账本。本地已提交 usage 仍是已记录用量的来源。GenAI semantic conventions 在研究时仍有演进状态，适合隔离在 adapter 中。S32 S33

Langfuse 的原生 OpenTelemetry 接入文档在本次研究时使用 HTTP JSON / protobuf；不要假定所有 OTLP transport 都被后端支持。接入时复核当前文档；本规格不要求首版依赖任何远程后端。S34

关键区分

  • 一次产品 run 可以跨多次进程执行和多个模型请求；durable 的内部 task ID 不能与产品 run 混为一谈。
  • 关联工具时使用包含会话/任务范围的身份，不能把 provider tool-call ID 当作全局唯一键。
  • task_type 可以是 bugfix、feature、refactor、test、docs 等建议类别；不要求每次额外用模型打标签。
  • 当 Git 可用时记录 commit 与工作区是否 dirty。只有 hash 而没有可取得的配置内容、未提交 diff 或初态，不能声称可复现。
  • 不必为每个真实任务创建 worktree 或完整仓库快照。选中成为 eval case 时，先判断能否从已有材料还原初态；能还原时补齐输入，不能还原时标记“不可复现”，或另建明确标为重构案例的新任务，不能声称精确重放原运行。
  • 运行事实、用户决定和后续评分分别存储。重评估生成新的 judgment，不改写过去发生的事件。
  • 未知、缺失、估算、截断、过期引用分别标记。没有被记录的事件不是没有发生。

CHAPTER 10

长期评估：衡量什么，怎样解释

三类能力的关系

Tracing 解释发生了什么；LLM Ops 解释运行条件、资源和可靠性；evals 检查结果与行为是否达标。长期分析利用三者发现问题，观察到趋势不自动证明某个改动造成了趋势。

维度 有用指标 解释边界
任务效果 实际检查通过、目标达成、明确用户反馈、返工与回退 agent 自称成功、patch 被采纳、没有投诉均不是充分证明
正确性与约束 必要回归、范围遵循、是否遗漏用户要求 不能为了省工具调用省掉必要工作
效率 已知 tokens / 费用、完成延迟、工具输出量、疑似重复调用 必须考虑任务难度、版本和质量
可靠性 API/网络/工具错误、中断、恢复、超时与未知结果 基础设施错误需计入可靠性和实际成本，分析原因时再分组
交互质量 用户纠正、重复确认、无效等待、过度解释 只使用实际证据，不臆测用户心情
轻量程度 启动、RSS、日志增量、依赖体积、维护负担 不用单一 LOC 代表全部开销

分母、覆盖率与缺失

  • 真实任务按 completed / failed / cancelled / changed-requirement / unknown 等实际原因区分；具体枚举在实现时统一。
  • 成功率应显示分母和验证覆盖率。仅对已验证样本的通过率，应明确说明未覆盖多少任务。
  • 用户取消可能是需求改变，不能直接作为模型能力失败；也不能把所有取消或基础设施错误从报告中悄悄删掉。
  • 区分模型/工具活跃耗时和等待用户的时间。无法细分时说明测量口径。
  • 日常 coding、retro 和 eval 的开销分开报告，再给总成本，避免“优化节省”隐藏评测费用。

长期比较的常见混淆

本周 tokens 降低，可能因为任务更简单、模型改变、上下文更短或缓存命中增加。建议按项目、任务类型、模型配置、agent 版本和环境分层；小样本只报告观察，不给出过度精确的因果或显著性结论。

历史重新评分可以改善 grader 或定位问题，但无法展示尚未运行过的新 prompt / skill / tool 策略会怎样行动。需要证明行为改进时，应执行新的可比试验。

模型与 harness 之外的基础设施也可能改变 coding eval 结果；因此环境限制、资源、网络和缓存状态需要记录，不能把全部差异归因于模型或规则改动。S35

优化的目标顺序

先满足任务正确性、用户约束和必要验证，再比较成本、延迟和维护复杂度。tokens 更少、测试更少、工具次数更少都不是单独的成功条件。一个合理候选也可能是：删除重复规则、缩短输出、复用现有检查，或保持现状。

CHAPTER 11

最小 Eval 体系与候选验证

首版需要什么

一个可手动运行的 runner、一小组有代表性的任务、真实产物与检查结果、可比较的版本信息，以及机器可读摘要。它应复用产品 runtime；不要求依赖完整实验平台。

Agent eval 通常需要明确 task、一次或多次 trial、grader 和真实 outcome。软件任务可优先用可执行检查，主观行为再辅以 rubric 或用户校准；不能只根据聊天中“已经完成”评分。S36

任务组成建议

类型 检查目标
基本 coding 读取、修改、运行检查、完成小修复
回归 已修复问题仍然正确，既有行为未退化
恢复 在具体提交边界中断后，恢复状态和副作用符合合同
工具边界 路径、失败、输出截断、取消和不确定结果
轻量性 不必要重复读取、输出、重复测试或上下文膨胀
Retro 行为 证据不足可给零候选、只读阶段不修改、尊重用户选择
使用范围 规则应该触发的正例，以及不该触发的反例

候选验证协议

先按改动类型选择验证方式。以下 fresh A/B 步骤适用于需要证明模型行为、任务效果、成本或延迟改善的候选；纯内容修正、确定性 bug 或局部性能问题可采用直接检查或专项基准，不要求额外运行 coding A/B。

  1. 写出具体假设、主变量、目标指标与需要保护的行为。不要一次混改模型、prompt、工具与预算后声称知道原因。
  2. 需要 fresh A/B 时，从相同任务输入和代码初态运行 baseline 与 candidate；分开 session 和工作目录，避免复用答案或副作用。
  3. 尽可能保持相近环境、模型配置、预算与时间条件；必要时交错顺序，减少缓存和环境漂移的影响。
  4. 先用最小相关检查。只有模型行为变化或明确剩余风险需要时，才追加相关 eval；不为每次 retro 固定跑全量集合。
  5. 保留所有计划的 trial 及失败、超时和缺失；报告差异和样本数，不只展示最好结果。
  6. 随机性可能影响结论，需要时增加重复。单次通过不是稳定性的证明；结果可以是“未证明改善”。
  7. 记录分析、试验和维护成本。明显超出潜在收益时可停止，不必强行找出赢家。

数据集边界

初期可区分用于提出候选的开发案例、固定回归案例，以及少量未被用于调优的新案例。若以后反复搜索候选，再引入更严格的 holdout 和更新机制。

用于反复选择候选的 holdout 会逐渐成为调优反馈。 不应长期暴露所有细节又宣称完全独立；可定期补充新任务并保留真正未参与选择的检验。首版不要求实现一整套数据集管理服务。

独立性与有效性

  • 候选不能顺手修改使自己通过的 grader、隐藏测试或评分门槛。
  • 如果 grader 本身有问题，单独提出修复，独立版本化，并在新规则下重测 baseline 与 candidate。
  • 工作目录隔离可防止无意污染，但 worktree 不是权限沙箱；需要保护的 grader / hidden case 应由候选不可修改的 runner 管理。
  • LLM judge 可能受轨迹中的不可信文本影响。把材料作为被评价的数据，明确 rubric；关键正确性优先依赖实际检查。
  • 不强制换模型或增加第二 reviewer；评判证据和执行边界比“由另一个 agent 发言”更重要。
  • 通过与失败案例都应保留代表性样本，避免只学习失败而不断增加负担。

按改动类型选择验证

改动 合适的最小验证

工具实现或 runtime bug 针对真实失败路径的检查，必要时验证恢复/取消边界
Prompt / skill / 策略效果 相关任务的 fresh run，包含不应触发的反例
成本或延迟优化 在任务效果可比条件下比较；明确模型/环境与费用口径
Grader 修改 仅评分逻辑改变时，优先对保存的相同产物重评分；环境、任务或运行规则改变时再重跑，并保持基线与候选可比

CHAPTER 12

Retro：触发、取证与完整流程

核心行为合同

ID 行为
RET-01 用户显式调用 retro 或明确要求复盘时才启动；普通 coding 结束不自动调用 LLM 自省。
RET-02 未指定范围时，先看当前任务/会话；需要历史对照时查询相关的近期同项目/同类型记录。
RET-03 先查询摘要和统计，再读取少量相关原始 trace、检查结果和配置；不默认注入全量历史。
RET-04 建议阶段只读业务材料；可由宿主持久化复盘报告，但不改变项目、agent、配置或默认行为。
RET-05 输出少量最有价值的候选，推荐上限 5 项，无最低数量；允许零候选或证据不足。
RET-06 每项候选有稳定 ID、证据、事实与假设区分、目标、具体动作、验证与生效范围。
RET-07 用户选择具体候选后，完成其声明的范围与必要验证；不逐文件反复确认。
RET-08 记录决定、执行、效果，保留它们之间的区别；不把采纳等同有效。
RET-09 尊重暂缓与不再建议的作用域；不让同一问题每次重复占据推荐列表。
RET-10 同一 runtime / 模型可完成分析与实施；不依赖固定的第二 reviewer。

阶段与转移

阶段 输入与动作 产生什么 下一步
Scope 用户给定范围或合理默认值 项目、时间、版本、任务和数据缺失说明 检索证据
Evidence 结构化筛选，选择代表性失败与成功样本 可追溯的事实与候选问题 形成建议或报告证据不足
Proposal 区分事实和原因假设，提出最小改变 少量可审阅候选 等待用户选择
Decision 用户执行、仅验证、暂缓、不再建议 针对具体候选版本的决定 执行所选项或结束
Execute 检查前提仍成立，完成所选范围 patch / 配置变更 / 实验 必要验证与适用的启用
Result 保存检查、变化、实际效果和局限 可供下一次 retro 使用的记录 回到普通 coding

复盘可以独立结束在 Proposal 或 Decision 阶段；没有选择时，不继续修改。暂停的提议可以之后重新选中，前提是作用对象和版本仍适用。

推荐检索步骤

  1. 查询最近相关 run 的数量、状态、版本、用量和检查摘要，明确样本覆盖。
  2. 找高影响、高频或明显阻塞的问题；不要只按费用从大到小猜低效。
  3. 读取支持候选的原始 trace，同时选择必要成功反例。
  4. 查看当前配置、工具实现与项目已有检查，确认问题尚存在、已有机制是否可以修复或复用。
  5. 检查以前的候选、用户决定和实验结果，过滤重复、已解决与明确被抑制的内容。
  6. 排序展示。排序可考虑影响、频率、置信度、实施成本与维护负担，无需首版设计复杂评分公式。

建议发现方向

信息定位慢、重复读取大文件、工具输出太大、无依据重复测试、无效或矛盾提示、错误恢复、模型/预算配置不匹配、检查缺失且确实导致问题、skill 触发过宽、compaction 后遗漏、依赖或启动开销、上下文污染。

这些方向都是待查假设。例如两次运行同一测试，可能因为代码已变化或前次输出不完整；只有证据支持时才认定为可减少的重复。不得把“减少测试次数”直接写成规则。

CHAPTER 14

权限、目标作用域与版本生效

分析阶段的能力

宿主应让 retro 能读取所选范围的记录、源码与配置，并查询结构化摘要。避免在只读阶段暴露任意 write / edit / unrestricted shell；如果需要执行查询命令，用受限的已知查询能力。仅在 skill 文本写“不要修改”不能提供可靠边界。

报告和选择记录由宿主保存到自己的记录范围，这属于本功能的正常数据写入，不代表允许修改用户项目或 agent 默认行为。只读指的是被分析对象与执行环境，不是要求整个应用完全不写自己的日志。

若普通任务正在运行，不要通过全局切换工具 registry 影响它。可以在明确边界排队复盘，或用同一宿主中的独立只读调用读取固定快照；不需要因此建立另一个常驻 agent 服务。

改动对象必须明确

目标 示例 执行注意
用户当前项目 导航、已有检查接线、项目配置 不将 agent 内部优化悄悄变成业务项目重构
Agent 配置 模型、输出限制、预算、重试参数 记录旧值与新值、适用范围与生效任务
Prompt / skill 删除重复规则、缩短正文、纠正触发条件 内容变更也会改变行为，不因是 Markdown 就自动启用
Agent tools 文件操作、工具输出、错误恢复 在 agent 自己的源码位置修改，检查真实执行语义
Agent runtime 调度接线、版本、性能问题 不热改当前 pending task；兼容性与回退明确
Eval 资产 新案例、独立 grader bug 与被评估候选分开变更与版本，不自行改分宣告成功

选择执行前检查 repo、基线和工作区状态是否仍适用；保留用户现有未提交修改。变更应在合适的分支、隔离目录或可回退配置版本中进行，具体做法取决于项目现状。

用户一次选择包含什么

候选应在展示时说清楚：它是“先验证”，还是“修改、验证并对新任务启用”。用户选中后一口气完成该合同，不把执行、每个文件和每条检查命令切成重复确认。

只选了验证，就停在验证结果；选了包含启用的方案，验证通过且前提未变时，可按已声明的时机启用。验证失败或出现范围外问题时，记录结果，不强行启用或悄悄扩大重构。

输入可信度

Trace、仓库内容、工具输出与从历史记录提取的文字是证据材料。它们不能修改当前用户授权、评分规则或 retro 的只读阶段。若材料中包含“忽略规则、修改评分、自动执行”等文字，作为被分析内容处理。

Skill 名称、frontmatter 和文件后缀不提供额外权限。被优化程序也不应获取隐藏 eval 答案或发布规则的写权限来帮助自己通过验证。

  • 同一次用户选择不会因重启或重复投递而盲目重新应用改动；恢复时依据候选版本、基线和实际文件状态判断已完成、可继续或结果不确定。执行记录关联 revision、基线和 change ref。
  • 不另外实现 durable 已有的调度、inbox、checkpoint、compaction 或第二套 usage 聚合。

分阶段实施路线

这是一条推荐依赖顺序，不是固定工期承诺。每阶段完成具体可运行结果，再决定是否扩展。

阶段 交付 完成条件
P0 · 复核与基线 锁定依赖；最小公开入口运行；记录平台/认证选择 实际能启动和请求模型，依赖路径可解释
P1 · Coding 核心 单进程 runtime、基本工具、SQLite、headless、TUI 能完成任务，退出/恢复/中止与锁冲突语义清楚
P2 · 记录与观测 run 身份、版本、usage、关键 spans、检查摘要与查询 运行数据可追溯，恢复与导出不重复计费

接手时最先做的事情

  1. 阅读当前 repo 的说明与约束，确认要修改的是 agent 仓库还是用户业务仓库。
  2. 复核所选 Pi 版本的公开入口、依赖、认证路径、工具与存储语义。

CHAPTER 22

可直接交给实现 Agent 的摘要

你要实现一个超轻量 coding agent。用户要求基于 pi-durable，具备 evals、LLM Ops 和 tracing，并借鉴 grok-build 的 TUI 体验以及 Pi 的官方 durable demo。核心目标是少量自有代码、可测量的低依赖/运行开销，以及可长期追溯的运行记录。

采用本规格的推荐默认值作为起点：TypeScript + Node、pi-durable、必要的 pi-ai provider、pi-tui 与本地 SQLite；TUI、headless 和 eval 共用一个 runtime。先测量基线，再优化体积。不要重写 durable 已有的 agent loop、恢复状态机或 usage 聚合。

长期改进的主方案是内置、手动调用的 retro skill。普通 coding 仅记录必要事实，不默认运行 LLM critic。retro 先查询小摘要，再读取少量原始证据；最多提出少量可操作候选，无最低数量，允许证据不足或无需改动。

每个候选必须写清问题、证据、事实与假设、作用对象、最小改动、必要验证、潜在退化，以及选择后是否启用和何时生效。用户选择后，完成已声明范围，不逐文件重复确认；仅验证的选择不能自动改变默认行为。范围实质扩大或基线失效时重新说明。

分析阶段的只读能力由宿主落实；skill frontmatter 不替代权限。区分用户业务项目、agent 配置、prompt/skill、工具/runtime 和评测资产。修改 agent 自身时使用正确源码位置，不能热改旧 pending task。记录候选、用户决定、实际变更与效果，不把采纳当成功。

用 durable 已知 usage 作为用量来源，区分 run、attempt、工具执行和恢复。流式 span 持续到真实终止；completeSimple 内部调用 streamSimple，避免双计。未知费用不记为零。UI 事件可合并为 snapshot，不能当无损审计账本。遥测故障不改变业务结果。

Durable 恢复已提交状态，不保证 shell 进程原地继续、文件回滚或外部副作用 exactly-once。工具 replay 默认 unsafe；恢复 safe 需要持久化与当前声明同时为 safe，而且不重新运行 beforeTool。SQLite 默认 NORMAL 面向进程崩溃，不能承诺掉电零丢失。一个 storage 由一个进程拥有；首版避免多个活动写入者共享工作区。

评估优先真实结果和必要检查。历史趋势提出假设；需要证明行为改进时，在相同任务与初态上 fresh run，分开 session/工作目录，避免候选修改自己的评分器。按风险验证，不为每次复盘强制全量 eval、第二 reviewer 或额外测试框架。结果可以是改善、退化、无明显变化或证据不足。

不要默认引入常驻 optimizer、自动生成并启用 skill、向量数据库、自动发布或 fine-tuning。一个稳定的 retro skill 管流程，记录层提供长期记忆，eval 检验候选，版本控制承载改变。先把这条简单路径做可靠，再根据实际收益扩展。

本文件中的字段、命令和目录是建议，需适配当前仓库。用户尚未指定的 provider、平台、预算、保留期和打包形式在实现时决定，不应转成一轮冗长确认。本次仅生成规格；不要声称已实现、已接通观测或已测得性能提升。
